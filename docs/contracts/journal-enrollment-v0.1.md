# Journal enrollment and historical lookup v0.1

**Accepted on November 21, 2026.** After a lost response, a caller needs to know whether the host has a receipt, has only partial evidence, or can't trust the store. This contract specifies how a host enrolls one private workspace and how another process reads its history. [ADR 0009](../adr/0009-durable-agent-run-reconciliation.md) governs the recovery decisions. This contract specifies a local disk format and the evidence required to implement it. GAAP's frozen public contracts retain their existing versions.

## Deployment and ownership

Use one Linux host, one dedicated service account, one private workspace and one fixed storage slot. Qualify a local ext4 filesystem with ordered data journaling, write barriers enabled, working file and directory sync, and same-directory atomic replacement. Use the same device for the host control directory, journal directory and workspace. The host verifies the mount type and configured volume for each opened directory. An overlay, network mount, alternate mount alias or unqualified configuration yields `unsupported_storage`. A macOS development checkout can validate examples. The production profile needs its own Linux qualification. [Linux ext4 documentation](https://docs.kernel.org/admin-guide/ext4.html) · [Linux file and directory sync](https://man7.org/linux/man-pages/man2/fsync.2.html)

A trusted host provisions the slot once, before GAAP can enroll it. It supplies two owner-private directories outside the mutable workspace. The control directory contains a stable `lock` and `anchor.json`. The journal directory holds the snapshot. The host pins their expected paths and identities and assigns the workspace and store IDs. Every cooperating GAAP process uses this same slot. The provisioner must know the workspace has never participated, reserve it exclusively, and durably establish the directories, lock and initial `unused` anchor before handing them to the service. An absent or unreadable anchor can't establish a fresh installation. Creating a second slot for the same workspace, restoring an old valid slot or importing an existing workspace with unknown history requires a separate design. These trust assumptions apply across process restarts.

Host configuration supplies the current authenticated principal, enrollment privilege, and read permission for the workspace and that principal's submissions. Request data can't select roots, rights, policy implementations or principal identities. Cooperating writers take an exclusive `flock` on the permanent lock file. Readers open that existing file read-only and take a shared lock. A bounded lock wait returns `busy` on timeout. Both paths require the existing lock. Hold the lock through validation, publication and final confirmation, or through the complete history read. Prevent children from inheriting the lock. Proving that every executor has stopped before a new dispatch belongs to slice 2. [Linux lock semantics](https://man7.org/linux/man-pages/man2/flock.2.html)

Open from trusted directory descriptors. Reject symlink components and paths that cross away from the configured volume. Check directory and lock identities against host configuration and check opened objects against their directory entries. Require the expected owner, private directories (0700), regular state files (0600), one link for regular files and different directories for control, journal and workspace. Reject containment in either direction among these three directories. The stable directory and lock identities must survive replacement of an individual snapshot. Changed identities after relocation, recreation or remount hold the store. Hostile same-user writes, raw-disk tampering and rollback of the entire trusted installation are outside this profile.

## Format and limits

Both files use UTF-8 RFC 8785 canonical JSON with no BOM, trailing newline or duplicate member names. Reject unknown fields, invalid Unicode, unsupported versions and noncanonical stored bytes. Check lengths while reading, before allocation or decompression. This profile accepts uncompressed files only. Preserve proposal string contents, array order and Unicode code points. A later submission may use different whitespace or object member order. Parse that submission strictly, canonicalize it and compare the complete canonical bytes under its original proposal profile. [JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785)

| Type or bound | Accepted v0.1 rule |
| --- | --- |
| IDs and digests | Host-issued workspace, store and attempt IDs are 32 lowercase hex characters from 16 random bytes. Principal and submission keys are case-sensitive opaque ASCII identifiers, 1–128 bytes from letters, digits, dot, underscore or hyphen. The host supplies the principal and the caller supplies the key. A digest is `sha256:` plus 64 lowercase hex digits. Public request, run and effect IDs follow the frozen validators. |
| Host identities | Record the absolute canonical UTF-8 path, device, inode, UID and permission bits of each pinned directory and the lock. Device and inode use unsigned decimal strings without leading zeros except `0`. UID and mode are nonnegative JSON integers. A file replacement changes the journal inode, so compare that inode within each operation and use the generation/digest binding across publications. |
| Capacity | Maximum 16 KiB for the anchor, 8 MiB for the entire journal, 12 retained attempts, 256 KiB per raw proposal and 256 KiB per canonical proposal. All byte limits are inclusive. Count JSON escaping, record overhead and retained evidence inside the journal limit. Limit nesting to 64 JSON containers and reject integers outside the nonnegative JCS-safe range in local counters. Reject overflow before staging. Fixed snapshot and history sizes follow the [local reference](../../examples/submitted-proposal/src/coding/mod.rs). These admission ceilings need qualification on the target filesystem. |
| Retention | Record the bounds at enrollment. Retain all original keys, IDs, evidence and sealed bytes for the lifetime of the slot. A full valid store remains readable. Further work that can't fit receives `capacity`. ENOSPC or an I/O error while reading produces `unavailable`. History eviction, automatic pruning and online migration require a new decision. |

**Host anchor.** The closed object has `format` = `gaap.journal-anchor/0.1`, `workspace_id`, `store_id`, `workspace`, `control`, `store`, `lock` (the four host identity records above, with fields `path,dev,ino,uid,mode`), `profile_digest`, `limits`, `phase`, `generation` and `journal_digest`. The limits object has exactly `anchor_bytes,journal_bytes,attempts,raw_proposal_bytes,canonical_proposal_bytes,depth`, set to the six limits above. The configured, retained host profile identified by `profile_digest` binds the proposal type, supported historical policy/capability identities and contract versions. Read permissions come from current host policy. Phase is `unused`, `reserved` or `active`. An active anchor requires a nonnegative safe integer generation and a digest. Both fields must be null in every other phase. Host startup must have independent access to the original profile and trusted identity configuration. Compare all IDs, paths, identities, original profile digest and limits to the independent provisioning record at enrollment and on each read. The host retains an authenticated, immutable copy of the original profile and its evidence resolver, archive and observation roles. The profile digest hashes its canonical JSON bytes. Reject an incomplete handoff. A policy claimed in the journal can't serve as its own allowlist.

**Journal.** Its closed top-level object has `format` = `gaap.journal/0.1`, `workspace_id`, `store_id`, `profile_digest`, `generation` and `attempts`. Bind the same IDs and profile as the anchor. Enrollment writes generation 0 and an empty array. Every later publication increments the generation by one, preserves every prior fact and retains the original admission order. Stop at the maximum safe integer. Hash the entire canonical journal for the anchor. A digest detects alteration relative to that independently held anchor. It can't authenticate a hostile writer that can replace both files.

**Generation-zero byte vector.** For these example identities the exact file is the single line below, ending at the closing brace. Its anchor's `journal_digest` is `sha256:743c01de7884aa322fcc7ad28985d73aa54b262bee4ed657a7636a9a3b5b2be7`. Adding a newline or accepting a different store ID must fail validation.

```json
{"attempts":[],"format":"gaap.journal/0.1","generation":0,"profile_digest":"sha256:3333333333333333333333333333333333333333333333333333333333333333","store_id":"22222222222222222222222222222222","workspace_id":"11111111111111111111111111111111"}
```

A historical attempt is a closed object with the following required members. It has an authenticated `principal`, `key`, host-issued `attempt_id`, typed `proposal`, `proposal_digest`, original `run_request`, original `effect_request` and ordered `facts`. A configured proposal decoder defines a closed type, its mapping to the two requests and its admissible non-secret input. Retain the full canonical representation as the embedded JSON value. For the first reference decoder use the [local file change](../../examples/submitted-proposal/src/coding/mod.rs) with exactly four required strings, `path,content,plan,base_digest`. The host must reject inputs requiring credential storage before retention. A digest alone can't stand in for proposal bytes. Scope key uniqueness to the principal. Enforce per-kind uniqueness across admissions for run request, run, attempt and effect IDs. Require exactly one proposed effect at sequence 1 and bind its idempotency key to that attempt.

Validate the complete snapshot, including other attempts, before answering a key lookup. The four public digest domains remain SHA-256 of canonical run request, effect request, effect result **body** and receipt **body** respectively. Verify sealed objects under original trusted policy bindings with the [Agent Run](agent-run-v0.1.md) and [Protected Effect](protected-effect-v0.1.md) validators. Check the links between the objects too. A receipt decision binds the same effect request and subject. An attempted tool execution references the exact result digest. An early refusal can legitimately have zero executions. Local device/inode checks don't replace portable artifact or subject digests.

## Historical facts the reader may return

Slice 1 creates empty history at enrollment. Its reader accepts the fact encoding below and returns `partial` for an unsealed prefix or `published` for an original sealed receipt. An intent alone proves non-dispatch only after writer quiescence and intact ordering are established. Report the independently observed effect separately from completion. A future producer must meet slice 2's execution and fencing requirements before writing live attempts.

### Attempt payload encoding

Each fact is a closed object with three required members, `tag`, `binding` and `payload`. Compute `binding` as the digest of the canonical JSON array `[workspace_id,store_id,profile_digest,principal,key,attempt_id,proposal_digest,run_request_digest,effect_request_digest]`. Use that same binding throughout the attempt. Each table row lists **all** members of its closed payload. All are required, including nullable members. Embedded public types use their frozen v0.1.0 JSON representations. [Run types](../../src/contracts/model.rs) · [Effect types](../../src/contracts/protected_effect/model.rs)

| Tag | Payload members and types |
| --- | --- |
| `intent` | `run_request_digest,effect_request_digest,proposed_artifact_digest` are digests. The first two hash the retained requests. The third hashes the exact UTF-8 bytes of the proposal's `content`. Its `base_digest` equals the run and effect subjects' digest. Its `plan` equals the run's task instructions. The effect's `input_digest` equals the proposal digest. |
| `dispatch` | `before` is a FileObservation. `executor` is an ExecutorIdentity. `decisions` is the ordered array of original RunEvent protected-effect decisions that allowed this invocation. `checked_at_ms` is a nonnegative JCS-safe Unix epoch millisecond. `checks` is an array of GrantCheck. `reserved` is an EffectUsage estimate. `usage_floor` is cumulative ResourceUsage. The unique attempt ID also identifies this single executor invocation. |
| `observed` | `disposition` is one of `replaced`, `not_started`, `stopped_before_rename` or `unresolved`. `after` is a FileObservation or null. `source` is an ObserverRef or null. `usage_floor` is cumulative ResourceUsage. The disposition describes what the host established about the target rename. |
| `verified` | `event` is the original RunEvent verification object. Its actor IDs, subject digest, verdict and evidence references describe the independent verifier's returned observation. `usage_floor` is cumulative ResourceUsage. |
| `published` | `receipt` is an entire sealed TerminalRunReceipt. `result` is the corresponding sealed ProtectedEffectResult or null if the engine produced none. Preserve the original envelopes, including their digest fields. |

A FileObservation has exactly `subject,file,artifact_digest`. The Subject is the original frozen repository or artifact subject. The local `file` has exactly `path,dev,ino,uid,mode` in the enrolled host identity encoding and refers to the original target under that workspace. The portable `artifact_digest` hashes the target's exact file bytes. Check the historical path against the enrolled root and the proposal path, and validate subject identity using the retained profile. A history lookup doesn't inspect the current target to decide what happened earlier.

A GrantCheck has exactly `approval,source`. The approval is a frozen ApprovalReference. The source is an ObserverRef from the host's configured grant validity and revocation source at `checked_at_ms`. Include every approval used. An empty array is valid only when the historical policy allowed dispatch without an individual grant. An ObserverRef has exactly `actor_id,evidence`, a nonempty string and a frozen EvidenceReference. Its locator must be present. Map it through the trusted archive's read-only index with bounded reads. Never follow a caller-supplied path or URL. Use the retained host profile to resolve the locator, verify the digest over the original evidence bytes and verify the actor's role. A historical reference grants no current rights.

Start with exactly one `intent`. Any nonempty prefix of an allowed path is valid. The next tags are intent → dispatch or published, dispatch → observed, observed → verified or published, and verified → published. Publication ends the attempt. Reject repeated, out-of-order or unknown tags, including reconciliation and dispute records. A dispatch with no observation keeps the workspace held.

For dispatch, require a matching pre-effect subject, historically trusted executor and original allowing gate decisions, including permission for this exact effect and subject. Validate their order and applicable policy, capability, schema, sandbox, budget and grant bindings against the retained profile and requests. Compare every usage component monotonically through the facts and against final receipt usage. Keep the estimate separate from measured lower bounds.

For a known disposition, require independent live evidence from the configured host observer tied to this store, attempt, effect, target and interval. A replacement requires observation of this invocation's rename and its output FileObservation, whose artifact hash matches the proposed bytes. For `not_started` or `stopped_before_rename`, require evidence covering every possible commit through the invocation's definitive stop and a null `after`. For `unresolved`, require a null `after`, retain available source evidence and keep the hold. An executor error or a later byte match can't settle the disposition. A known replacement survives a failed run or failed verifier.

Verification requires a recorded replacement, a profile-trusted verifier different from the implementer, and evidence bound to the output subject. At publication verify both envelopes and their cross-references. Compare the recorded dispatch decisions and verification event with the matching receipt events, including their original sequence numbers. Check the result's pre-effect subject, executor and sandbox against any recorded invocation it describes. A recorded replacement with a reported post-effect subject requires agreement with `after.subject`. After dispatch, publication requires a result. Reject an executed replacement result paired with proven non-execution, or a denied/awaiting-authority result paired with a proven rename. For an observed replacement retain the original failure or interruption if the result reports one. An unresolved observation keeps the hold across publication. Direct publication from intent requires a non-completed receipt with no tool execution or mutation and either a null result or an unexecuted refusal. Completion requires `replaced`, a passing verifier, the engine's final fresh-subject completion decision and the matching executed result. Return original evidence under current read permission. No prefix permits a reader to resume or seal a run.

For qualification, the existing lost-response test produces a linked local-file run request, effect request, result and completed receipt. Another process reopens the history and observes the file's inode and bytes. Reuse that tuple to exercise frozen bindings and collect the proposed fact fields at their actual observation points. The two standalone completed contract examples contain different effect bindings and provide a negative pairing. [Local-file test](../../examples/submitted-proposal/tests/test_protocol.py#L72-L117) · [Reference history validator](../../examples/submitted-proposal/src/coding/mod.rs#L102-L201)

Reject a skipped prerequisite, a fact appended after sealing that attempts to reopen the run, duplicate/conflicting bindings, or evidence needed to interpret a fact that fails validation. A future compatible reader must report admitted operator rulings separately and retain a hold for conflicting evidence. A passing verification event alone can't yield a completed receipt. Historical records can outlive execution policy, subject changes and expired grants. They remain readable only while the original profile can be validated and the principal has current read rights. V0.1 has no migration, version negotiation, import or downgrade path. Keep unrecognized data for diagnosis. The conference ledger and Python design model use other formats.

## Enrollment and lookup

The host exposes two logical operations. The adapter guide maps these operations to its host-invoked CLI.

1. **Enroll the configured slot.** Authorize the host operator, acquire the exclusive lock and validate the provisioned identities and anchor. Only an `unused` anchor and an empty journal directory can begin first enrollment. Durably replace the anchor with `reserved`. Only the writer that completed this reservation and still holds the lock may create generation 0. Sync the new journal, publish it at `journal.json` without replacing any existing entry, and sync the journal directory. Reopen and validate the exact IDs, generation and digest before replacing the anchor with `active`. The active-anchor rename makes enrollment visible. Its directory sync must succeed before the host acknowledges enrollment.
2. **Look up one historical submission.** Authorize the reader before revealing existence. Derive the principal from the host, accept a key and optionally the complete proposal for duplicate comparison. Take the shared lock, open existing files read-only, check identities, bounds, canonical bytes, profile and the entire record graph. An active anchor and matching journal identify a confirmed snapshot. Return the original fact set for this principal/key, or `conflict` for different canonical bytes. A missing key in this validated history returns `absent` within the caller's namespace. A workspace-wide unresolved effect still blocks any fresh dispatch under any key. Return the hold without disclosing another principal's history. An unauthorized caller gets the same `forbidden` response irrespective of key existence.

For each replacement, create a private, previously unused staging file in the destination directory, write all bytes, flush, sync the file, check close errors and recheck held identities and expected prior state under the same lock. Rename within the directory, then sync its directory descriptor. Use no-replace publication for the first journal. Never overwrite a foreign entry, copy across filesystems, or delete another process's stage. In the later writer, the journal rename publishes the new evidence. After successful journal directory sync, a separate active-anchor replacement confirms its generation and digest. A matching, visible anchor witnesses the earlier journal sync. It can't attest that its own directory sync completed. Historical facts describe the validated generation visible to this reader. They grant no permission for a new execution or guarantee that an unacknowledged anchor rename will survive power loss.

A repeated explicit enrollment with the same active binding validates existing history, never rewrites it and returns the existing enrollment. After a lost acknowledgment or process termination on a healthy volume, the authorized enrollment process must recheck the matching active anchor and sync the anchor and its directory before acknowledging its current durability. A reported storage or writeback I/O error instead puts the volume on an operator hold. The trusted host must keep the faulted volume unavailable across restarts until independent storage recovery and requalification. A later successful sync alone can't clear that hold. Corrupt, conflicting or incomplete state stops that path. A retained reservation after interruption returns `incomplete_enrollment`. Preserve the slot for operator diagnosis. This version doesn't recreate it or resolve an interrupted reservation automatically.

| Validated state at lookup | Reply and recovery |
| --- | --- |
| Authentic unused anchor, empty journal directory | `not_enrolled`. An authorized operator can enroll the fixed slot. |
| Reserved anchor with no journal or its exact generation 0 journal | `incomplete_enrollment`. Preserve both directories for the operator. |
| Active anchor, exact matching journal and valid records | Return `absent`, `conflict`, `partial` or `published` as applicable, with the visible generation and workspace hold. Historical lookup never acknowledges a previous caller's delivery. |
| Active anchor, journal one generation ahead | `unconfirmed`. Preserve both files. The selected format can't establish lineage from this pair alone. Withhold all keyed answers. |
| Unused anchor with a journal, conflicting reservation, missing or older active journal, larger generation gap, same generation with changed bytes, or an unexpected entry that conflicts with ownership | `invalid_store`. Preserve the bytes and hold the workspace for diagnosis. |
| Current read authorization denied, lock busy, unsupported profile/format, I/O failure | Return `forbidden`, `busy`, `unsupported_storage` or `unavailable` for the observed condition. Retry a busy read after the writer exits. Missing provisions and known storage faults need operator attention. |

Never select an older snapshot to permit execution. Responses identify the phase, whether trusted history was available, and the next safe action, subject to read authorization. Inspection changes no content, authority, budget or execution state.

## Qualification required before production use

Run the future enrollment binary and an independently started lookup process against the declared Linux volume. Use fresh processes and directories and observe actual sync calls, file identities, byte digests and workspace contents from outside the writer. Test cuts immediately before and after every named step. Keep the evidence for each cut, including the command result, surviving state, lookup response and subsequent enrollment behavior.

| Operation or cut | Expected evidence after failure or restart |
| --- | --- |
| Authorize, open directories, inspect mount and entries, open/acquire lock, read/parse/validate anchor and journal | Wrong principal, denied access, wrong mount, hardlink/symlink, moved root, mismatched tuple, parse error, impossible transition or unknown version yields refusal before mutation. Interleave another process between observation and lock acquisition, and between validation and rename. Two enrollment processes for the same slot yield at most one binding. An alternate store/workspace or lock replacement is refused. |
| Stage each anchor update and initial journal | Inject exclusive-create collision, short/failed write, failed flush, failed file sync, close error and ENOSPC individually for each file. Prior canonical bytes survive every pre-rename cut. Initial journal failure after reservation leaves a held reservation. Preserve unrelated stages. |
| Reserve, publish generation 0 and activate | Kill the process immediately before/after each rename and before/after each directory sync. Failed reservation sync prevents journal creation. Failed journal sync prevents activation. Failed activation sync yields no durable acknowledgment. An empty, validated, confirmed generation becomes readable after activation. Missing confirmed data always holds. |
| Finish or lose a response | Stop after activation sync and before reply. An independent enrollment returns the same IDs, lookup sees the same empty generation, and the workspace and journal bytes remain unchanged. Failure to remove an owned stage after commit adds a warning. Unknown stage ownership preserves the file. |
| Read populated, full and damaged histories | Use an actual engine-produced request/result/receipt tuple and an independent effect observation. Exercise identical and changed proposal bytes, another principal's key, reused IDs, exact and one-over byte/count bounds, mismatched result/receipt pairs, missing store and an unsupported payload. Record all keyed replies and independently hash files before/after each read. |
| Separate effects from completion | Supply two histories with the same dispatch bytes and different physical outcomes, a known write followed by failed verification, a published refusal and a lost response after a sealed completion. Confirm no replay, no fresh IDs, no changed counters or rewritten receipts. A terminal result with unknown effect keeps the workspace hold. Slice 2 must repeat its own production checks around actual target and receipt commits. |

Process termination tests leave the kernel running. Claims about power loss require separate abrupt storage or VM restart tests on the specified filesystem, mount and device configuration. Existing [model fixtures](../../tests/durable_run_model/) and [local transaction checks](../../examples/submitted-proposal/TRANSACTION.md) inform these cases. The adapter guide identifies the process tests and platform used to qualify enrollment and lookup. Power-loss qualification requires separate evidence.
