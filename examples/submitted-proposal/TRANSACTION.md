# Local proposal commit and recovery checks

The canonical local record is `operator/state.json`. Its replacement publishes one full ledger snapshot. Filesystem mutation and ledger or receipt publication aren't one atomic transaction, and this profile has no exactly-once recovery guarantee. The host records an in-flight marker before effect dispatch so interruption preserves an explicit uncertainty window.

| State | Commit or transition | Observable state and recovery |
| --- | --- | --- |
| Cancelled or expired while queued | Stop waiting for admission or the snapshot lock before writing a marker. | No run, effect or receipt exists; an explicit retry can make its first admission. |
| Prepared | Validate the strict input, current session, subject and canonical requests under the session lock. | No effect; reject malformed input without a marker. |
| Admitted | Sync and rename the ledger containing `inflight`. | A restart refuses dispatch while that marker remains. |
| Admission durability refused | Publish an abort snapshot before the engine starts. | No effect has run; a successful abort clears the marker. A failed abort leaves the visible state for inspection. |
| Snapshot byte limit exceeded | Refuse publication before creating a temporary ledger. | Keep the prior readable snapshot. After an effect, its retained in-flight marker blocks replay. |
| Staged | Create, write, chmod, flush and sync a temporary file; recheck the source snapshot. | A pre-rename failure preserves the current target and produces a failed effect. |
| Effect committed | Rename the staged file over the allowed target. | The write exists even if verification or later publication fails. |
| Result published | Sync and rename the full ledger with the result. | Inspection revalidates canonical receipts and evidence; duplicates return that receipt. |
| Uncertain | A post-effect observation or result-publication operation fails. | Preserve the target and marker; refuse another dispatch. Retain this root and inspect it. |
| Published with warning | Directory sync fails after the result rename. | Save the observed warning in a follow-up snapshot so inspection and duplicates retain it. If warning publication fails, return an error and retain the visible receipt and actual effect. |

The initializer syncs initial files, the workspace directory, the session root and its parent before publishing the ready ledger. It then syncs the ledger directory. Any refused sync returns an error and preserves the visible root; a namespace failure before the ledger leaves an incomplete root without a ready record. Each response exposes `publication_durability: null`: a snapshot can't record the outcome of its own later directory sync. An observed result-publication warning gets a separate save attempt. If storage also refuses that warning, the caller receives an error and historical durability remains unavailable; a visible completed receipt still describes its known effect.

All writers that change an active workspace must acquire the `operator/lock` file lock first, then the lock on the existing operator directory, and hold both through their writes. This matches the host's lock order. Read-only inspectors use only the directory lock. An ordinary editor doesn't follow that protocol: a save between the final subject check and rename can be overwritten, and the post-commit snapshot can't recover it. Stop all host writers before editing with such a tool. Keep `operator/state.json` host-owned; manual ledger changes grant no recovery authority.

The writer rechecks observed ownership and subject before replacement and refuses changes it observes before commit. It has no atomic compare-and-replace primitive for writers that ignore its locks. Unrecognized schema, changed capability trust, changed policy, relocated directories, symlinked session roots or files, hardlinks and tampered evidence are rejected without repairing or deleting the stored state. The reference assumes a controlled trusted process and local filesystem; hostile concurrent path replacement and power-loss continuation need separate designs.

The persistence profile uses a single local JSON snapshot and an admission lock for cooperating writers. A separate lock on the existing operator directory serializes inspection with the entire admitted effect/publication span. Opening a saved session validates under that same snapshot lock. Queued admission hasn't taken it yet, so a lock-waiting request can still be observed and cancelled through status. Both waits poll for interruption against the request's original deadline and return before admission without changing the ledger. A final control check refuses expiry during preparation before writing the marker. Once admission publishes the in-flight marker, the worker retains its actual outcome on interruption. Admission doesn't guarantee completion within the remaining request budget. An interrupted zero-effect run still has an immutable terminal receipt; exact duplicates return it. A deliberate fresh proposal uses a new plan/current subject and receives a new host-issued run, without reopening the earlier receipt. Parent aliases resolve to the same canonical parent during initialization and opening; the recorded canonical root and filesystem identities still have to match. That keeps history inspectable and publication simple, at the cost of rewriting the bounded ledger and serializing admission. Twelve saved runs and an 8 MiB snapshot limit bound storage; result-publication refusal retains the previous snapshot and its in-flight marker. The versioned session schema rejects incompatible records. Changed policy or capability trust requires a fresh, separately initialized root rather than migration or automatic trust refresh.

Session subjects bind local device, inode and mode alongside file content, so those subject identities belong to this filesystem instance. A hash of file bytes can identify equal content across copies, but it doesn't authenticate a writer or make the session portable. Ownership, link and mode checks protect the trusted local process's path handling; a same-user process that edits the files can bypass that process's contract. Durable portable evidence and reconciliation need the separately accepted design.

The migrated Rust fault matrix exercises dispatch/abort/result create, write, flush, file sync, rename and directory sync; target create, write, mode change, flush, file sync and rename; post-commit uncertainty; concurrent edits; and verifier drift. Identity, open/read, parse and validation refusal paths use actual links, moved roots, malformed proposals and edited records. Each case inspects actual files and the production ledger consumer. Concurrent public-interface readers check coherent history/files across twelve large proposals, accepting only explicit lock-deadline refusals under sustained contention; CLI/MCP checks reopen a parent alias without changing saved trust and still reject leaf symlinks and relocated roots. A cooperating external writer uses both locks while admission queues; its edit causes a stale-input refusal before any marker. A later coordinated edit survives historical duplicate delivery. A byte-limit regression checks that oversized snapshot publication leaves the previous state readable and permits a fresh admission when no effect ran. Initial directory-creation failures preserve an incomplete root for operator inspection; no auto-cleanup or uninstall operation is provided.

Verifier regressions reject a function that misses the two-item case and a function that memorizes the published examples. They also exercise repeated squaring from both rounding and Boolean comparisons, confirming that intermediate arithmetic stays in the float domain. Host-seeded samples are repeatable from the recorded request digest.

The Python lifecycle checks initialize, inspect, submit, restart, read historical outcomes and repeat delivery through the public CLI/MCP surfaces. The original launcher-specific selection, inspector and recipe-publication tests stay with the preserved conference checkout. This port carries their relevant saved-history and no-reset behavior through the new CLI; it doesn't introduce another launcher or UI.

Run the matrix with:

```bash
cargo test --manifest-path examples/submitted-proposal/Cargo.toml --locked
python3 -B -m unittest discover -s examples/submitted-proposal/tests -p 'test_*.py'
```

An uncertain effect stays uncertain for the lifetime of this session. File snapshots, saved requests, effect records, receipts and external observations can support operator diagnosis; inspection grants no authority to clear the marker, reclassify the effect or admit a retry. This version admits no human attestation, provider response or independent observation as reconciliation evidence. Editing the ledger or deleting its marker would bypass the admission contract. A separately accepted #32 design must define the evidence, its admission authority and fresh run/attempt rules before recovery can be implemented. GAAP retains authority over its bounded run and effects; ThreadLoop retains authority over its outer lifecycle.

Approval continuation and resumption remain deferred to #32, including handling approval expiry and revocation after interruption. Terminal receipts, including authority-required outcomes, stay immutable and never reopen. A fresh proposal receives fresh host-issued run/request IDs and current policy, subject and capability checks. Returning a historical duplicate grants no new authority.

## Regression coverage from the conference fixture

| Conference behavior | Coverage in this reference |
| --- | --- |
| Restart, receipt preservation and exact duplicates | `test_discovery_completion_denial_restart_and_historical_duplicate` checks these through independent MCP and CLI consumers. |
| Existing roots and unsafe adoption | Initialization refuses existing roots; Rust identity tests reject links and relocated sessions. Commands require an explicit root. |
| Protected writes and publication failures | Rust fault matrices cover staged writes, admission, abort, result and warning publication, with actual file and saved-history inspection. |
| Launcher selection, browser URLs and saved Goose recipes | These features remain in the original preserved fixture. This reference exposes CLI/MCP commands and an ephemeral Goose acceptance profile; it has no launcher, browser-route or recipe-publication entry point to exercise. |

The original launcher tests still cover that local UI and its saved selection. Porting those features and tests would publish additional conference work beyond this adapter. The adapter's public interface and the CLI/MCP behavior that this PR ships have their own in-repository regressions.
